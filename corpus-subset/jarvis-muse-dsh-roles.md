# jarvis / Muse / DSH の役割整理（2026-11-09）

## 結論
**重なっているのは「エージェント体験」の層だけ**。階層を分ければ競合しない。
推奨は「**Muse＝外出先のUX / DSH＝開発・作業の実行環境 / jarvis＝統制・記憶・イベントの基盤**」。

## 現状の機能マッピング

| 機能 | jarvis | Muse | DSH |
|---|---|---|---|
| 会話UX | △（OpenCode経由） | ◎（スマホ・音声・Gadget） | ◎（Web/GUI） |
| ツール実行 | ○（MCPゲートウェイ） | ○（MCPコネクタ） | ◎（MCPクライアント＋内蔵ツール） |
| 外部サービス連携 | ○（自作アダプタ） | ◎（Meta/サードパーティConnector） | △（MCP経由） |
| 自宅・HA・Android連携 | ◎（jarvis-event） | △（クラウド経由のみ） | △ |
| 長期記憶 | ◎（PostgreSQL＋Qdrant） | △（Meta側） | △（セッション） |
| ポリシー・承認・監査 | ◎（jarvis-policy） | △（Metaの権限UI） | △（権限モード） |
| 開発・コード作業 | △（OpenCode/code-server） | × | ◎ |
| 自己ホスト/データ所有 | ◎ | ×（クラウド） | ◎ |
| 運用コスト | 中（常駐） | 低（SaaS） | 中 |

## 重複が問題になるポイント
1. **エージェントの二重持ち**: jarvisがOpenCodeランタイムを持ち、DSHもランタイムを持つ
2. **外部連携の二重実装**: カレンダー/通知/Web検索をMuseとjarvisで別々に作る
3. **記憶の二重管理**: どちらが正か決まっていないと文脈が分裂する
4. **攻撃面の増加**: 外部公開されたエージェントが2つになる
5. **コスト/保守**: どちらもLLM呼び出し・監視・更新が必要

## 推奨する役割分担（境界）

```
[Muse]  外出先の音声・通知・Meta連携          ← UXクライアント
   │ MCP（読み取り中心・トークン認証）
[DSH]   デスクトップの開発/作業エージェント   ← 実行環境（ACPでZedからも）
   │ MCP
[jarvis] 自宅のコントロールプレーン           ← 基盤（policy/memory/events/mcp-gw）
```

### 境界ルール
- **記憶の正はjarvis-contextのみ**。Muse/DSHは読み書きをMCP経由で行い、独自記憶を持たない
- **権限・承認の正はjarvis-policyのみ**。特権操作（HA操作・書き込み・送信）はjarvis-mcp-gw経由
- **エージェントランタイムの正はDSH**。jarvisはランタイムを持たず、OpenCodeは「レガシー実装」として段階縮小
- **MuseはMetaエコシステムのConnectorを担当**し、自前で同じ連携を作らない
- Museからの特権操作は**初期は禁止（読み取りのみ）**。必要になったら個別ツールを承認付きで開放

## ADR-0002との整合
ADR-0002は「jarvisをランタイム非依存の基盤へ」と決めた。
今回の整理はその徹底であり、**jarvisからランタイム所有を外す**（OpenCodeは任意profile）ことで
Muse/DSHとの重複が解消する。

## 段階的な簡素化
1. jarvis: OpenCode/code-serverを**オプション化**（停止しても基盤は動く）
2. DSH: MCPクライアントで jarvis `/mcp` に接続（読み取り系から）
3. Muse: jarvis `/mcp` を読み取り専用で接続（必要ならトークン認証＋公開経路）
4. 重複する連携（検索・通知・カレンダー）はMuseへ寄せ、jarvisから削除
5. 最終形: **DSH=実行 / jarvis=記憶・統制 / Muse=外出先UX**

## 注意
- MuseはMetaクラウド依存。機密性の高い記憶をどこまで渡すかは別途ポリシーで決める
- jarvisを「基盤」に徹すると、単体では会話できなくなる（OpenCode停止時）。それは意図通り
- DSHとjarvisの同居は、ポリシー境界（jarvis-policy）を迂回しない設計が前提
